# Routing Matrix — 评分矩阵与拆分规则

> 版本: 2.0.0 | 更新: 2026-06-07

## 五维评分矩阵

### 维度定义

| 维度 | 字段名 | 权重 | 评估方法 |
|------|--------|------|----------|
| 代码行数预估 | `loc_estimate` | 20% | 根据需求描述推断改动规模 |
| 涉及文件数 | `file_count` | 20% | 单文件/多文件/跨模块 |
| 数据库变更 | `db_changes` | 20% | 是否涉及 DDL/DML、迁移脚本 |
| 跨模块依赖 | `cross_module` | 20% | 是否跨越多个业务域或服务 |
| 风险等级 | `risk_level` | 20% | 是否涉及认证/支付/核心链路 |

### 评分细则

```json
{
  "scoring": {
    "loc_estimate": {
      "1": {"range": "0-50", "desc": "微小改动，单个方法或配置"},
      "2": {"range": "50-200", "desc": "小规模，单个类或几个方法"},
      "3": {"range": "200-500", "desc": "中等规模，多个类或模块"},
      "4": {"range": "500+", "desc": "大规模，需要拆分考虑"}
    },
    "file_count": {
      "1": {"range": "1", "desc": "单文件修改"},
      "2": {"range": "2-5", "desc": "少量文件，同模块内"},
      "3": {"range": "5-15", "desc": "多文件，可能跨目录"},
      "4": {"range": "15+", "desc": "大量文件，需要拆分"}
    },
    "db_changes": {
      "0": {"desc": "无数据库变更"},
      "2": {"desc": "仅 DML（数据操作）"},
      "3": {"desc": "DDL 变更（表结构）"},
      "4": {"desc": "数据库迁移脚本"}
    },
    "cross_module": {
      "1": {"desc": "单文件改动，无跨模块"},
      "2": {"desc": "单模块内多文件"},
      "3": {"desc": "跨模块但同服务"},
      "4": {"desc": "跨服务或跨系统"}
    },
    "risk_level": {
      "1": {"desc": "配置、日志、文档"},
      "2": {"desc": "普通业务逻辑"},
      "3": {"desc": "认证、支付、权限"},
      "4": {"desc": "核心基础设施、数据链路"}
    }
  }
}
```

### 阈值规则

```json
{
  "thresholds": {
    "light": {"max_score": 8, "desc": "简单任务，快速处理"},
    "riper_one": {"min_score": 9, "max_score": 15, "desc": "中等任务，标准流程"},
    "super_dev": {"min_score": 16, "desc": "复杂任务，完整治理"}
  }
}
```

## 强制路由规则

以下场景不走评分，直接强制路由：

| 场景 | 强制路由 | 原因 |
|------|----------|------|
| 用户显式声明「强制 light 模式」 | light | 用户意愿优先 |
| 用户显式声明「强制 riper-one 模式」 | riper-one | 用户意愿优先 |
| 用户显式声明「强制 super-dev 模式」 | super-dev | 用户意愿优先 |
| 涉及认证核心代码 | super-dev | 高风险必须重型治理 |
| 涉及支付核心代码 | super-dev | 高风险必须重型治理 |
| 纯 typo 修正 | light (zero) | 机械性改动无需流程 |
| 日志级别调整 | light (zero) | 机械性改动无需流程 |
| 配置值变更 | light (zero) | 机械性改动无需流程 |
| 新项目/新模块搭建 | super-dev | 需要完整研究和架构 |
| Bug 修复且根因明确 | light (fast) | 目标清晰无需重型分析 |

## 大任务自动拆分

### 触发条件

- **LOC 阈值**: 预估代码行数 > 500 行
- **文件阈值**: 涉及文件数 > 15 个

任一条件满足即触发拆分。

### 拆分策略

| 拆分依据 | 适用场景 | 示例 |
|----------|----------|------|
| 按功能模块 | 跨模块改动 | 订单模块 + 支付模块 + 通知模块 |
| 按文件变更范围 | 大规模重构 | 数据层 → 服务层 → 控制层 |
| 按数据库表 | 涉及多表 | 每张表的变更独立一个子任务 |
| 按流程阶段 | 多阶段工作 | 先 DDL → 再代码 → 再测试 |

### 拆分输出格式

```json
{
  "split_decision": {
    "trigger": "LOC=680 > 500",
    "strategy": "按功能模块拆分",
    "subtasks": [
      {
        "id": "T-001-a",
        "scope": "数据库层变更",
        "loc_estimate": 150,
        "files": 3,
        "depends_on": []
      },
      {
        "id": "T-001-b",
        "scope": "服务层逻辑",
        "loc_estimate": 280,
        "files": 6,
        "depends_on": ["T-001-a"]
      },
      {
        "id": "T-001-c",
        "scope": "控制器和测试",
        "loc_estimate": 250,
        "files": 5,
        "depends_on": ["T-001-b"]
      }
    ],
    "execution_order": "sequential",
    "dependency": "T-001-a → T-001-b → T-001-c"
  }
}
```

### 拆分后处理

每个子任务独立拥有：
- 独立的 Spec 文档
- 独立的质量检查
- 独立的状态记录（harness-state.json 的 node_truth）
